第一部分：RMANRecovery Manager — CDB / PDB 的備份、還原、復原

觀念：Backup / Restore / Recover 差在哪

Backup把資料檔、控制檔、archivelog 複製成備份片
→
發生故障檔案遺失、誤刪資料
→
Restore從備份把檔案「拿回來」
資料停在備份當時
→
Recover套用 archived / online redo
把資料「往前推」
→
Open資料庫恢復服務
名詞意思練習重點
CDBContainer Database，容器資料庫。包含 CDB$ROOT、PDB$SEED 與所有 PDB。控制檔、redo、archivelog 都屬於 CDB 層級。連 rman target / 就是連到 CDB root，BACKUP DATABASE 會備份全部容器。
PDBPluggable Database，插入式資料庫，應用程式實際使用的資料庫。可以單獨備份、還原、做時間點還原，不影響其他 PDB。
Restore從備份把實體檔案寫回磁碟。只做 Restore 時，資料檔還是舊的，不能直接開啟。
Recover套用 redo（archivelog + online redo），把資料推進到故障前一刻或指定 SCN／時間。沒有完整的 archivelog 就只能還原到較早的時間點。
SCNSystem Change Number，資料庫的內部「時間戳」，每次 commit 都會往上加。做時間點還原時，用 SCN 比用時間更精準。

前置準備

R1

確認並開啟 ARCHIVELOG 模式

PrimarySQL*Plus
為什麼

NOARCHIVELOG 模式下，redo 寫滿後會被覆蓋，只能做「關機冷備份」，也只能還原到備份當下。開啟 ARCHIVELOG 後，每個寫滿的 redo 都會另存成 archivelog，RMAN 才能做線上（不停機）備份，也才能 Recover 到故障前一刻或任意時間點。Data Guard 也要求必須是 ARCHIVELOG。

SQL*Plus
sqlplus / as sysdba

-- 1) 先看目前模式
SELECT log_mode FROM v$database;
ARCHIVE LOG LIST

-- 2) 若為 NOARCHIVELOG 才需要下面步驟（會短暫停機）
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE ARCHIVELOG;
ALTER DATABASE OPEN;

-- 3) 讓 PDB 跟著 CDB 自動開啟
ALTER PLUGGABLE DATABASE ALL OPEN;
ALTER PLUGGABLE DATABASE ALL SAVE STATE;
指令意思
sqlplus / as sysdba
用作業系統認證（oracle 使用者屬於 dba 群組）以 SYSDBA 身分登入目前 ORACLE_SID 的 CDB root。
v$database.log_mode
顯示 ARCHIVELOG 或 NOARCHIVELOG。
ARCHIVE LOG LIST
SQL*Plus 指令，一次列出模式、歸檔位置、目前 log sequence。
SHUTDOWN IMMEDIATE
回滾未提交交易、中斷連線後正常關機，資料檔處於一致狀態。
STARTUP MOUNT
開啟執行個體並讀取控制檔，但不開資料檔。修改日誌模式必須在 MOUNT 狀態。
ALTER DATABASE ARCHIVELOG
把模式記錄到控制檔，之後寫滿的 redo 會由 ARCn 程序歸檔。
ALTER PLUGGABLE DATABASE ALL SAVE STATE
記住 PDB 目前為 OPEN，下次 CDB 重啟時自動開啟，不然 PDB 預設停在 MOUNTED。
預期結果

SELECT log_mode FROM v$database; 顯示 ARCHIVELOG；SHOW PDBS 中 {{PDB}} 為 READ WRITE。

R2

設定 Fast Recovery Area（FRA）

PrimarySQL*Plus
為什麼

FRA 是 Oracle 自動管理的復原專用區，archivelog、控制檔自動備份、flashback log 預設都放在這。設定空間上限後，Oracle 會依保留政策自動清掉過期檔案。若 FRA 塞滿，archivelog 寫不出去，整個資料庫會停住（ORA-00257），所以大小一定要抓夠。

OS + SQL*Plus
# OS：建立目錄（備份片另外放一個目錄，方便觀察）
mkdir -p {{ORABASE}}/fast_recovery_area
mkdir -p {{BKP}}

-- SQL*Plus：先設大小、再設路徑（順序不能反）
ALTER SYSTEM SET db_recovery_file_dest_size = 20G SCOPE=BOTH;
ALTER SYSTEM SET db_recovery_file_dest = '{{ORABASE}}/fast_recovery_area' SCOPE=BOTH;

-- 查使用率
SELECT name, space_limit/1024/1024/1024 AS limit_gb,
       space_used/1024/1024/1024 AS used_gb
FROM   v$recovery_file_dest;
指令意思
db_recovery_file_dest_size
FRA 可使用的空間上限。必須先設定，否則設定路徑時會出現 ORA-19802。
db_recovery_file_dest
FRA 的目錄。設定後 archivelog 預設會寫到 <FRA>/{{CDB}}/archivelog/日期/。
SCOPE=BOTH
同時改目前記憶體中的值與 spfile，重啟後仍有效。
v$recovery_file_dest
查看 FRA 的上限、已使用、可回收的空間。
R3

連線 RMAN 並設定預設組態

PrimaryRMAN
為什麼

先把常用設定存成預設值（CONFIGURE），之後每次備份只要下很短的指令，行為也一致。其中最重要的是控制檔自動備份：控制檔記錄了所有備份片的位置，若控制檔也遺失，就要靠 autobackup 找回它，否則 RMAN 不知道備份在哪。

RMAN
rman target /

SHOW ALL;

CONFIGURE CONTROLFILE AUTOBACKUP ON;
CONFIGURE CONTROLFILE AUTOBACKUP FORMAT FOR DEVICE TYPE DISK TO '{{BKP}}/cf_%F';
CONFIGURE RETENTION POLICY TO RECOVERY WINDOW OF 7 DAYS;
CONFIGURE DEVICE TYPE DISK PARALLELISM 2 BACKUP TYPE TO COMPRESSED BACKUPSET;
CONFIGURE CHANNEL DEVICE TYPE DISK FORMAT '{{BKP}}/%d_%T_%U.bkp';
CONFIGURE ARCHIVELOG DELETION POLICY TO BACKED UP 1 TIMES TO DISK;
指令意思
rman target /
以 OS 認證連到目前 ORACLE_SID 的資料庫（CDB root）。target 就是「要被備份／還原的資料庫」。
SHOW ALL
列出所有 RMAN 組態，有 # default 字樣的代表還沒改過。
CONTROLFILE AUTOBACKUP ON
每次備份結束、或結構變更（加資料檔）時，自動備份控制檔與 spfile。
AUTOBACKUP FORMAT ... '%F'
控制檔備份的檔名格式。%F 會產生含 DBID 與日期的檔名（c-DBID-日期-序號），還原時 RMAN 靠這個格式去找。
RECOVERY WINDOW OF 7 DAYS
保留政策：保證可以還原到過去 7 天內任一時間點，超出的備份會被判定為 OBSOLETE。
PARALLELISM 2
同時開 2 個 channel（備份程序）並行處理，加快速度。
COMPRESSED BACKUPSET
以壓縮的 backupset 格式輸出，只備份用過的區塊，體積較小。
FORMAT '%d_%T_%U.bkp'
備份片檔名：%d 資料庫名、%T 日期 YYYYMMDD、%U 保證唯一的識別碼。
ARCHIVELOG DELETION POLICY
archivelog 至少被備份過 1 次後才允許刪除，避免刪掉還沒備份的 log。
預期結果

每個 CONFIGURE 都回應 new RMAN configuration parameters are successfully stored。

R4

建立練習資料，並記下 DBID

PrimarySQL*Plus
為什麼

要有自己的資料表，還原後才能用筆數驗證「資料真的回來了」。把練習資料放在獨立的 tablespace，模擬單一資料檔遺失時就不會動到系統檔。DBID 是資料庫的唯一識別碼，控制檔全部遺失時 RMAN 要靠它找自動備份，所以要事先記下來（正式環境應寫進維運文件）。

SQL*Plus
sqlplus / as sysdba

-- 記下 DBID（S3 情境會用到）
SELECT dbid, name FROM v$database;

-- 切到 PDB 建練習資料
ALTER SESSION SET CONTAINER = {{PDB}};

CREATE TABLESPACE lab_ts
  DATAFILE '{{ORABASE}}/oradata/{{CDB}}/{{PDB}}/lab_ts01.dbf' SIZE 100M;

CREATE USER lab IDENTIFIED BY lab
  DEFAULT TABLESPACE lab_ts QUOTA UNLIMITED ON lab_ts;

CREATE TABLE lab.t1 AS SELECT * FROM all_objects;
SELECT COUNT(*) FROM lab.t1;
指令意思
ALTER SESSION SET CONTAINER
把目前連線切換到指定的 PDB，之後的 SQL 都在該 PDB 執行。
CREATE TABLESPACE ... DATAFILE
建立表空間並指定實體資料檔路徑。若資料庫使用 OMF，可以省略路徑。
QUOTA UNLIMITED ON lab_ts
允許 lab 使用者在 lab_ts 上無限制使用空間，否則建表會出現 ORA-01950。
CREATE TABLE ... AS SELECT
用查詢結果建表，快速灌入幾萬筆測試資料。
注意

練習資料一定要在 B1 備份之前建立。若先備份才建 tablespace，備份裡就沒有這個資料檔（雖然 RMAN 仍能用 archivelog 重建，但不是這份練習要看的情境）。

Backup：備份

B1

全 CDB 線上備份（含 archivelog）

PrimaryRMAN
為什麼

線上備份時資料仍在變動，備份出來的資料檔各自停在不同時間點（不一致）。還原時一定要搭配備份期間產生的 archivelog 才能 Recover 成一致狀態，所以用 PLUS ARCHIVELOG 把它們一起備份。從 CDB root 執行 BACKUP DATABASE 會涵蓋 root、seed 與所有 PDB。

RMAN
rman target /

BACKUP DATABASE PLUS ARCHIVELOG;

-- 看剛剛做了什麼
LIST BACKUP SUMMARY;
指令意思
BACKUP DATABASE
備份所有資料檔（CDB root + PDB$SEED + 所有 PDB）。因為 autobackup 已開，結束時會自動備份控制檔與 spfile。
PLUS ARCHIVELOG
RMAN 實際流程：① 切換 log 並備份現有 archivelog → ② 備份資料檔 → ③ 再切換 log，備份備份期間產生的 archivelog。確保備份本身就能復原到一致。
LIST BACKUP SUMMARY
列出備份清單，TY 欄位 B=backupset，LV 欄位 F=full、A=archivelog、0/1=增量層級。
預期結果

最後顯示 Finished Control File and SPFILE Autobackup；ls {{BKP}} 可以看到多個 .bkp 與 cf_c-... 檔案。

B2

增量備份：Level 0 / Level 1

PrimaryRMAN
為什麼

每天做全備份很耗時間與空間。常見做法是每週做一次 Level 0（基準），每天做 Level 1（只備份變動過的區塊）。注意：B1 的 BACKUP DATABASE 是「full」，不能當作增量的基準，增量一定要從 Level 0 開始。

RMAN
-- 基準備份（例如每週日）
BACKUP INCREMENTAL LEVEL 0 DATABASE PLUS ARCHIVELOG;

-- 模擬資料異動（在另一個 SQL*Plus 視窗）
--   ALTER SESSION SET CONTAINER = {{PDB}};
--   INSERT INTO lab.t1 SELECT * FROM lab.t1 WHERE ROWNUM <= 1000; COMMIT;

-- 差異增量（例如週一到週六）
BACKUP INCREMENTAL LEVEL 1 DATABASE PLUS ARCHIVELOG;

-- 累積增量（自上次 Level 0 以來所有變動）
BACKUP INCREMENTAL LEVEL 1 CUMULATIVE DATABASE;

LIST BACKUP SUMMARY;
指令意思
INCREMENTAL LEVEL 0
內容等同全備份，但會被標記為增量基準，後續 Level 1 以它為起點。
INCREMENTAL LEVEL 1
預設為 differential（差異）：只備份自上一次 Level 0 或 Level 1 以來變動的區塊，最小最快。
CUMULATIVE
累積增量：備份自上一次 Level 0 以來所有變動。體積較大，但還原時要套用的增量片數較少。
延伸

開啟 Block Change Tracking 可以讓 Level 1 不必掃描整個資料檔：ALTER DATABASE ENABLE BLOCK CHANGE TRACKING USING FILE '{{ORABASE}}/oradata/{{CDB}}/bct.chg';（Enterprise Edition 功能）

B3

只備份單一 PDB 或 CDB Root

PrimaryRMAN
為什麼

某個 PDB 要做大型變更（升版、匯入大量資料）前，只需要先備份那個 PDB，不用整個 CDB 都備。理解 CDB 與 PDB 備份範圍的差別，也是後續 PDB 還原的基礎。

RMAN
-- 方法 A：連在 CDB root（建議）
rman target /
BACKUP PLUGGABLE DATABASE {{PDB}} PLUS ARCHIVELOG;
BACKUP DATABASE ROOT;
LIST BACKUP OF PLUGGABLE DATABASE {{PDB}};

-- 方法 B：直接連到 PDB（透過 listener service）
rman target sys@{{PDB}}
BACKUP DATABASE;
指令意思
BACKUP PLUGGABLE DATABASE {{PDB}}
只備份該 PDB 的資料檔。可以一次列多個，用逗號分隔。
BACKUP DATABASE ROOT
只備份 CDB$ROOT 的資料檔（SYSTEM、SYSAUX、UNDO、USERS）。
rman target sys@{{PDB}}
直接連 PDB，此時 BACKUP DATABASE 只會備份這個 PDB。
注意

archivelog 屬於 CDB 層級，連在 PDB 時無法備份 archivelog，也無法做 PDB 還原。所以實務上建議一律從 CDB root 操作（方法 A）。

B4

檢查、驗證與清理備份

PrimaryRMAN
為什麼

「有備份」不等於「能還原」。VALIDATE 會實際讀取備份片確認可用，不會真的寫回檔案。CROSSCHECK 會比對紀錄與磁碟，抓出被手動刪除的備份。定期清掉過期備份，FRA 與備份目錄才不會塞滿。

RMAN
REPORT SCHEMA;                      -- 列出所有資料檔與編號（還原時常用）
REPORT NEED BACKUP;                 -- 依保留政策，哪些檔案還需要備份

RESTORE DATABASE VALIDATE;          -- 模擬還原：只讀不寫，確認備份片可用
RESTORE PLUGGABLE DATABASE {{PDB}} VALIDATE;
BACKUP VALIDATE CHECK LOGICAL DATABASE;   -- 檢查資料檔本身有無壞塊

CROSSCHECK BACKUP;
CROSSCHECK ARCHIVELOG ALL;
DELETE NOPROMPT EXPIRED BACKUP;
REPORT OBSOLETE;
DELETE NOPROMPT OBSOLETE;
指令意思
REPORT SCHEMA
顯示每個資料檔的編號（File）、所屬容器、tablespace 與路徑。
RESTORE ... VALIDATE
走一遍還原流程，挑出需要的備份片並讀取檢查，但不寫入資料檔。是最安全的還原演練。
BACKUP VALIDATE CHECK LOGICAL
不產生備份，只掃描線上資料檔的實體與邏輯損壞，結果寫入 v$database_block_corruption。
CROSSCHECK
逐一確認紀錄中的備份檔是否還在磁碟上，找不到的標記為 EXPIRED。
DELETE EXPIRED
只刪除「紀錄」，因為實體檔案本來就不在了。
REPORT / DELETE OBSOLETE
依 R3 設定的 7 天保留政策，列出／刪除已經不需要的備份（實體檔案也會刪）。

Restore + Recover：三個故障情境

情境故障還原範圍資料遺失CDB 需停機
S1PDB 的一個資料檔不見單一資料檔不會（完整復原）不用，只關該 PDB
S2使用者誤刪資料表整個 PDB 回到過去某個 SCN該 SCN 之後的 PDB 異動都會消失不用，只關該 PDB
S3控制檔 + 所有資料檔遺失整個 CDBonline redo 還在就不會要
S1

情境一：PDB 單一資料檔遺失

PrimarySQL*PlusOSRMAN
為什麼

這是最常見也最小範圍的故障。只要還原那一個檔案、再用 archivelog 把它推進到最新，其他 PDB 完全不受影響，也不會遺失資料。先把 PDB 關閉再搬檔案：Linux 上被開啟中的檔案即使被搬走，Oracle 仍握有檔案代碼，錯誤不會立刻出現，關閉後再開就能穩定重現 ORA-01157。

① 模擬故障
-- SQL*Plus（CDB root）
ALTER PLUGGABLE DATABASE {{PDB}} CLOSE IMMEDIATE;

# OS：把資料檔搬走（模擬遺失）
mkdir -p /tmp/lab_broken
mv {{ORABASE}}/oradata/{{CDB}}/{{PDB}}/lab_ts01.dbf /tmp/lab_broken/

-- SQL*Plus：嘗試開啟
ALTER PLUGGABLE DATABASE {{PDB}} OPEN;
-- 會出現 ORA-01157: cannot identify/lock data file NN
--        ORA-01110: data file NN: '.../lab_ts01.dbf'
② 還原 + 復原
rman target /

REPORT SCHEMA;    -- 確認遺失檔案的編號與路徑

RESTORE DATAFILE '{{ORABASE}}/oradata/{{CDB}}/{{PDB}}/lab_ts01.dbf';
RECOVER DATAFILE '{{ORABASE}}/oradata/{{CDB}}/{{PDB}}/lab_ts01.dbf';

ALTER PLUGGABLE DATABASE {{PDB}} OPEN;
指令意思
CLOSE IMMEDIATE
關閉指定 PDB（變成 MOUNTED），CDB 與其他 PDB 照常服務。
ORA-01157
Oracle 開檔時找不到或無法鎖定資料檔，錯誤訊息中的 NN 就是資料檔編號。
RESTORE DATAFILE '路徑'
從最近一份可用備份把該檔案寫回原位置。也可以寫檔案編號，例如 RESTORE DATAFILE 13;。
RECOVER DATAFILE
套用備份之後產生的 archivelog 與 online redo，把檔案推進到和資料庫其他部分相同的 SCN。RMAN 會自動找出需要的 log，必要時也會從備份還原 archivelog。
預期結果

PDB 成功開啟；ALTER SESSION SET CONTAINER={{PDB}}; SELECT COUNT(*) FROM lab.t1; 筆數與故障前相同（包含 B2 時新增的資料）。

變化練習

若整個 PDB 的資料檔都不見，可以改用 PDB 層級：RESTORE PLUGGABLE DATABASE {{PDB}}; RECOVER PLUGGABLE DATABASE {{PDB}};

S2

情境二：誤刪資料表 → PDB 時間點還原（PITR）

PrimarySQL*PlusRMAN
為什麼

誤刪資料是「邏輯錯誤」，檔案本身沒壞，所以 S1 的完整復原沒用（只會把刪除動作也套用回來）。這時要把 PDB 還原回「刪除之前」的 SCN，也就是 Point-In-Time Recovery。代價是：該 SCN 之後這個 PDB 所有的異動都會消失，但其他 PDB 不受影響。

① 記錄 SCN 並模擬誤刪
sqlplus / as sysdba

-- 確認 PDB 使用 local undo（12.2 之後預設為 TRUE）
SELECT property_value FROM database_properties
WHERE  property_name = 'LOCAL_UNDO_ENABLED';

ALTER SESSION SET CONTAINER = {{PDB}};
SELECT COUNT(*) FROM lab.t1;          -- 記下筆數
SELECT current_scn FROM v$database;   -- 記下 SCN，例如 3456789

DROP TABLE lab.t1 PURGE;              -- 模擬誤刪（PURGE 不進資源回收筒）
ALTER SESSION SET CONTAINER = CDB$ROOT;
ALTER SYSTEM SWITCH LOGFILE;          -- 讓刪除動作進入 archivelog
② PDB PITR
rman target /

ALTER PLUGGABLE DATABASE {{PDB}} CLOSE IMMEDIATE;

RUN {
  SET UNTIL SCN 3456789;              # ← 換成上一步記下的 SCN
  RESTORE PLUGGABLE DATABASE {{PDB}};
  RECOVER PLUGGABLE DATABASE {{PDB}};
}

ALTER PLUGGABLE DATABASE {{PDB}} OPEN RESETLOGS;
指令意思
LOCAL_UNDO_ENABLED
每個 PDB 有自己的 undo。為 TRUE 時 PDB PITR 直接就地完成；為 FALSE 時需加上 AUXILIARY DESTINATION '/路徑'，讓 RMAN 建立暫時的輔助執行個體。
current_scn
目前資料庫的 SCN。實務上若沒事先記錄，可用時間：SET UNTIL TIME "TO_DATE('2026-11-04 10:30:00','YYYY-MM-DD HH24:MI:SS')"。
DROP TABLE ... PURGE
直接刪除，不放進 recyclebin，所以無法用 FLASHBACK TABLE ... TO BEFORE DROP 救回，必須靠 RMAN。
RUN { }
把多個指令包成一組執行，SET UNTIL 只在這個區塊內生效。
SET UNTIL SCN n
指定復原終點：Recover 會停在 SCN n 之前，不會套用之後的 redo。
RESTORE / RECOVER PLUGGABLE DATABASE
只還原、復原該 PDB 的資料檔。
OPEN RESETLOGS
不完整復原後必須用 RESETLOGS 開啟，代表這個 PDB 開始新的「化身（incarnation）」，之前的時間線被截斷。
預期結果

SELECT COUNT(*) FROM lab.t1; 筆數與誤刪前相同。

延伸：只救一張表

若不想讓整個 PDB 倒退，RMAN 也能只救回單一資料表（會在背景建立輔助資料庫再匯出匯入）：
RECOVER TABLE lab.t1 OF PLUGGABLE DATABASE {{PDB}} UNTIL SCN 3456789 AUXILIARY DESTINATION '/tmp/aux' REMAP TABLE lab.t1:t1_restored;

S3

情境三：控制檔與所有資料檔遺失（整個 CDB）

PrimarySQL*PlusOSRMAN
為什麼

這是最嚴重的情境：控制檔不見，RMAN 連備份清單都沒有。復原順序一定是「控制檔 → MOUNT → 資料檔 → Recover → OPEN」：沒有控制檔就無法 MOUNT，沒有 MOUNT 就無法還原資料檔。這裡刻意保留 online redo log，所以仍可以復原到故障前一刻。

① 確認檔案位置並模擬毀損
sqlplus / as sysdba
SELECT name FROM v$controlfile;   -- 確認控制檔路徑
SELECT name FROM v$datafile;      -- 確認資料檔路徑
SELECT dbid FROM v$database;      -- 再次確認 DBID
SHUTDOWN ABORT;

# OS：搬走控制檔與資料檔（保留 redo log、spfile、密碼檔）
mkdir -p /tmp/lab_broken_cdb/{root,pdbseed,pdb}
mv {{ORABASE}}/oradata/{{CDB}}/*.dbf           /tmp/lab_broken_cdb/root/
mv {{ORABASE}}/oradata/{{CDB}}/pdbseed/*.dbf   /tmp/lab_broken_cdb/pdbseed/
mv {{ORABASE}}/oradata/{{CDB}}/{{PDB}}/*.dbf  /tmp/lab_broken_cdb/pdb/
mv {{ORABASE}}/oradata/{{CDB}}/control01.ctl   /tmp/lab_broken_cdb/
mv {{ORABASE}}/fast_recovery_area/{{CDB}}/control02.ctl /tmp/lab_broken_cdb/
# ↑ 控制檔路徑以 v$controlfile 查到的為準
② 還原控制檔 → 資料檔 → 復原
rman target /

SET DBID 1234567890;                 # ← 換成 R4 記下的 DBID
STARTUP NOMOUNT;

RUN {
  SET CONTROLFILE AUTOBACKUP FORMAT FOR DEVICE TYPE DISK TO '{{BKP}}/cf_%F';
  RESTORE CONTROLFILE FROM AUTOBACKUP;
}

ALTER DATABASE MOUNT;

RESTORE DATABASE;
RECOVER DATABASE;

ALTER DATABASE OPEN RESETLOGS;
ALTER PLUGGABLE DATABASE ALL OPEN;
指令意思
SHUTDOWN ABORT
立即終止執行個體，不做 checkpoint，等同斷電，用來模擬當機。
SET DBID
控制檔遺失時，RMAN 不知道自己面對哪個資料庫，需要 DBID 才能比對 autobackup 檔名中的 c-DBID-...。
STARTUP NOMOUNT
只用 spfile 啟動執行個體（記憶體與背景程序），不讀控制檔。這是還原控制檔唯一能用的狀態。
SET CONTROLFILE AUTOBACKUP FORMAT
R3 設定的格式存在控制檔裡，控制檔沒了 RMAN 就不知道，所以要在 RUN 區塊中再告訴它一次。若 autobackup 放在 FRA 預設位置則可省略。
RESTORE CONTROLFILE FROM AUTOBACKUP
找到最新的控制檔自動備份，寫回 control_files 參數指定的所有位置。
ALTER DATABASE MOUNT
讀取剛還原的控制檔，RMAN 才看得到備份清單。
RESTORE DATABASE
還原所有容器的資料檔。
RECOVER DATABASE
依序套用 archivelog，最後再套用仍存在的 online redo，推到故障前一刻。
OPEN RESETLOGS
使用「備份的控制檔」後一定要 RESETLOGS：會重建 online redo、log sequence 從 1 重新開始，產生新的 incarnation。
可能遇到

若 online redo 也一起遺失，RECOVER DATABASE 會在最後一個 archivelog 停下並出現 RMAN-06054（要求一個不存在的 log）。這代表最後幾筆交易救不回來，改用 RUN { SET UNTIL SEQUENCE n THREAD 1; RECOVER DATABASE; } 停在可用的最後一個 log，再 OPEN RESETLOGS。

預期結果

SHOW PDBS 全部為 READ WRITE，lab.t1 資料完整；temp file 會在開啟時自動重建。

為什麼

D1

D2

Primary：ARCHIVELOG、FORCE LOGGING、FLASHBACK

PrimarySQL*Plus
為什麼

Standby 完全靠 redo 同步。如果有人用 NOLOGGING 載入資料，這些變更不會產生 redo，Standby 上對應的區塊就會壞掉。FORCE LOGGING 強制所有動作都寫 redo。FLASHBACK 不是必要條件，但做 Failover 後要把舊 Primary 救回來（reinstate），必須靠它倒回時間點，否則只能整個重建。

SQL*Plus（Primary）
sqlplus / as sysdba

SELECT log_mode, force_logging, flashback_on FROM v$database;

-- 若還不是 ARCHIVELOG，先做 RMAN 章節的 R1
ALTER DATABASE FORCE LOGGING;
ALTER SYSTEM SET db_flashback_retention_target = 1440 SCOPE=BOTH;
ALTER DATABASE FLASHBACK ON;

SELECT log_mode, force_logging, flashback_on FROM v$database;
指令意思
FORCE LOGGING
資料庫層級強制記錄 redo，忽略物件或語句上的 NOLOGGING。
db_flashback_retention_target
希望 flashback log 能倒回多久，單位分鐘（1440 = 1 天）。flashback log 存在 FRA，需要 R2 的 FRA 已設定。
FLASHBACK ON
開始產生 flashback log，19c 可在 OPEN 狀態下直接開啟。
預期結果

三個欄位分別為 ARCHIVELOG、YES、YES。

D3

Primary：建立 Standby Redo Log（SRL）

PrimarySQL*Plus
為什麼

Standby 收到的 redo 先寫進 SRL，才能做「即時套用（Real-Time Apply）」，不用等 Primary 切換 log 才同步，延遲從幾分鐘降到幾秒。在 Primary 也建好 SRL 有兩個好處：DUPLICATE 時會一起複製到 Standby，而且 Switchover 後舊 Primary 變成 Standby 時馬上就能用。

SQL*Plus（Primary）
-- 看現有 online redo 的組數與大小
SELECT group#, thread#, bytes/1024/1024 AS mb FROM v$log;
SELECT group#, member FROM v$logfile ORDER BY group#;

-- 假設 online redo 有 3 組、每組 200M → SRL 建 4 組、每組 200M
ALTER DATABASE ADD STANDBY LOGFILE THREAD 1 GROUP 11 ('{{ORABASE}}/oradata/{{CDB}}/srl11.log') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE THREAD 1 GROUP 12 ('{{ORABASE}}/oradata/{{CDB}}/srl12.log') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE THREAD 1 GROUP 13 ('{{ORABASE}}/oradata/{{CDB}}/srl13.log') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE THREAD 1 GROUP 14 ('{{ORABASE}}/oradata/{{CDB}}/srl14.log') SIZE 200M;

SELECT group#, thread#, bytes/1024/1024 AS mb, status FROM v$standby_log;
指令意思
v$log
online redo 的組別、大小、狀態。SRL 大小必須與它相同。
ADD STANDBY LOGFILE
建立 Standby 專用的 redo log 組，Primary 角色時不會被使用。
組數規則
每個 thread 的 SRL 組數 = online redo 組數 + 1，確保 Standby 來不及歸檔時仍有空的 SRL 可接收。
GROUP 11~14
組號不能與 online redo 重複，用 11 起跳方便辨識。
D4

Primary：設定 Data Guard 初始化參數

PrimarySQL*Plus
為什麼

這組參數告訴 Primary：Data Guard 成員有誰、redo 要送到哪、怎麼送；也預先寫好「當自己變成 Standby 時」要向誰補 log。之後 DUPLICATE 會以這份 spfile 為基礎產生 Standby 的參數，所以在 Primary 先設好最省事。

SQL*Plus（Primary）
SHOW PARAMETER db_unique_name      -- 確認為 {{CDB}}

ALTER SYSTEM SET log_archive_config = 'DG_CONFIG=({{CDB}},{{STB}})' SCOPE=BOTH;

ALTER SYSTEM SET log_archive_dest_1 =
  'LOCATION=USE_DB_RECOVERY_FILE_DEST VALID_FOR=(ALL_LOGFILES,ALL_ROLES) DB_UNIQUE_NAME={{CDB}}'
  SCOPE=BOTH;

ALTER SYSTEM SET log_archive_dest_2 =
  'SERVICE={{STB}} ASYNC VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE) DB_UNIQUE_NAME={{STB}}'
  SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_state_2 = ENABLE SCOPE=BOTH;

ALTER SYSTEM SET fal_server = '{{STB}}' SCOPE=BOTH;
ALTER SYSTEM SET standby_file_management = AUTO SCOPE=BOTH;
ALTER SYSTEM SET log_archive_max_processes = 4 SCOPE=BOTH;

SHOW PARAMETER remote_login_passwordfile   -- 應為 EXCLUSIVE
指令意思
log_archive_config DG_CONFIG
列出這組 Data Guard 的所有 DB_UNIQUE_NAME，只有名單中的資料庫可以互傳 redo。
log_archive_dest_1 LOCATION
本機歸檔位置，USE_DB_RECOVERY_FILE_DEST 表示放在 FRA。
VALID_FOR=(ALL_LOGFILES,ALL_ROLES)
不論自己是 Primary 或 Standby、不論 online 或 standby log，都要在本機歸檔。
log_archive_dest_2 SERVICE
遠端目的地。SERVICE={{STB}} 是 tnsnames.ora 中的別名（D5 設定）。
ASYNC
非同步傳送，對應 Maximum Performance 保護模式（預設）。
VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE)
只有自己是 Primary 時才送 redo，變成 Standby 後自動停止這個目的地。
DB_UNIQUE_NAME={{STB}}
指明對方身分，必須存在於 DG_CONFIG 中。
fal_server
Fetch Archive Log：自己是 Standby 時，發現缺 log（gap）要向誰要。
standby_file_management=AUTO
Primary 新增或刪除資料檔時，Standby 自動跟著建立／刪除，否則 Standby 的 MRP 會停下來。
remote_login_passwordfile=EXCLUSIVE
允許 SYS 透過密碼檔遠端登入，redo 傳送就是用這個方式驗證。
注意

此時 Standby 還不存在，log_archive_dest_2 會出現錯誤（ORA-12514 / ORA-12541），alert log 有錯誤訊息屬正常現象，D9 完成後就會恢復。

Standby：建立目錄並啟動到 NOMOUNT

StandbyOSSQL*Plus
為什麼

RMAN DUPLICATE 需要一個已經啟動的「空」執行個體（auxiliary）來接收檔案。這個執行個體只要最少參數（只要 db_name）就能 NOMOUNT，真正的 spfile 會由 DUPLICATE 從 Primary 複製過來再修改。資料檔目錄要事先建立，因為這裡沿用和 Primary 相同的路徑。

OS（Standby，oracle）
# 與 Primary 相同的資料檔、控制檔、FRA 路徑
mkdir -p {{ORABASE}}/oradata/{{CDB}}/pdbseed
mkdir -p {{ORABASE}}/oradata/{{CDB}}/{{PDB}}
mkdir -p {{ORABASE}}/fast_recovery_area/{{CDB}}
mkdir -p {{ORABASE}}/admin/{{STB}}/adump

# 登記到 oratab，方便 . oraenv 切換
echo "{{STB}}:{{OHOME}}:N" >> /etc/oratab

# 最小 pfile
echo "*.db_name='{{CDB}}'" > /tmp/init{{STB}}.ora

export ORACLE_SID={{STB}}
sqlplus / as sysdba
SQL*Plus（Standby）
STARTUP NOMOUNT PFILE='/tmp/init{{STB}}.ora';
EXIT
指令意思
mkdir -p 相同路徑
DUPLICATE 加上 NOFILENAMECHECK 時，檔案會放到和 Primary 一樣的位置，目錄必須已存在。路徑不同時要改用 db_file_name_convert／log_file_name_convert。
/etc/oratab
記錄 SID 與 ORACLE_HOME 的對應，. oraenv 與開機自動啟動會讀它。
*.db_name
必須與 Primary 的 DB_NAME 相同，這是唯一必要的參數。
STARTUP NOMOUNT PFILE=
用指定的 pfile 啟動執行個體，不讀控制檔，等待 RMAN 連入。
預期結果

顯示 ORACLE instance started.；在 Primary 執行 sqlplus sys@{{STB}} as sysdba 能成功連入（狀態為 STARTED）。

D8

RMAN DUPLICATE FROM ACTIVE DATABASE 建立 Standby

PrimaryRMAN
為什麼

Standby 必須是 Primary 的實體複製品（同 DBID、同區塊內容）。FROM ACTIVE DATABASE 直接透過網路從線上 Primary 複製，不需要先做備份再搬檔案，Primary 不用停機。FOR STANDBY 會建立 standby 類型的控制檔，讓它成為 Standby 而不是新的獨立資料庫。

RMAN（在 Primary 執行）
rman TARGET sys@{{CDB}} AUXILIARY sys@{{STB}}

DUPLICATE TARGET DATABASE
  FOR STANDBY
  FROM ACTIVE DATABASE
  DORECOVER
  SPFILE
    SET db_unique_name   = '{{STB}}'
    SET log_archive_dest_1 = 'LOCATION=USE_DB_RECOVERY_FILE_DEST VALID_FOR=(ALL_LOGFILES,ALL_ROLES) DB_UNIQUE_NAME={{STB}}'
    SET log_archive_dest_2 = 'SERVICE={{CDB}} ASYNC VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE) DB_UNIQUE_NAME={{CDB}}'
    SET fal_server       = '{{CDB}}'
    SET audit_file_dest  = '{{ORABASE}}/admin/{{STB}}/adump'
  NOFILENAMECHECK;
指令意思
TARGET sys@{{CDB}}
來源資料庫（Primary），透過 TNS 連線並輸入 SYS 密碼。
AUXILIARY sys@{{STB}}
目的端（D7 啟動的 NOMOUNT 執行個體），靠 D5 的靜態註冊與 UR=A 才連得到。
FOR STANDBY
建立 physical standby：standby 控制檔、相同 DBID。
FROM ACTIVE DATABASE
直接從線上資料庫透過網路傳資料檔，不使用既有備份。
DORECOVER
複製完後順便套用 archivelog，讓 Standby 追到接近最新。
SPFILE SET ...
把 Primary 的 spfile 複製到 Standby，並覆寫指定參數。角色相關參數要「反過來」：dest_2 與 fal_server 指向 Primary。
NOFILENAMECHECK
允許兩邊檔案路徑相同。因為在不同主機上，這樣設定是安全的。
預期結果

最後顯示 Finished Duplicate Db。Standby 被重新啟動到 MOUNT，並使用新的 spfile{{STB}}.ora。

常見卡點
  • ORA-12514 / RMAN-04006：Standby listener 靜態註冊或 UR=A 沒設好（回到 D5）。
  • ORA-01017：密碼檔不一致（回到 D6）。
  • ORA-19504 / 找不到目錄：Standby 少建了資料檔目錄（回到 D7）。
D9

Standby：啟動 Redo Apply（MRP）

StandbySQL*Plus
為什麼

DUPLICATE 只負責「複製」，接收到的 redo 還需要有程序持續套用，Standby 的資料才會跟上 Primary。MRP 就是這個背景程序。有 SRL 時，19c 預設即為 Real-Time Apply。

SQL*Plus（Standby）
export ORACLE_SID={{STB}}
sqlplus / as sysdba

SELECT name, db_unique_name, database_role, open_mode FROM v$database;
SELECT group#, thread#, bytes/1024/1024 AS mb, status FROM v$standby_log;

ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;

-- 確認 MRP 在執行
SELECT process, status, thread#, sequence#, block# FROM v$managed_standby
WHERE  process LIKE 'MRP%' OR process LIKE 'RFS%';
指令意思
database_role
應為 PHYSICAL STANDBY；open_mode 為 MOUNTED。
RECOVER MANAGED STANDBY DATABASE
啟動受管理的復原程序 MRP0，持續套用收到的 redo。
DISCONNECT FROM SESSION
讓 MRP 在背景執行，SQL*Plus 立即返回、可以離開。
v$managed_standby
顯示 Data Guard 相關程序。MRP0 狀態 APPLYING_LOG 或 WAIT_FOR_LOG 都是正常；RFS 代表正在接收 redo。（19c 也可用 v$dataguard_process）
授權提醒

Standby 在 OPEN READ ONLY 狀態下同時執行 MRP，就是 Active Data Guard，需要額外授權。只要保持 MOUNTED 套用就不需要。

V2

確認 redo 有送出（Primary 端）

PrimarySQL*Plus
為什麼

先確認 Primary 這端送得出去。dest_2 有錯誤時，Primary 不會停止服務（ASYNC），只會默默累積落差，所以要主動檢查。

SQL*Plus（Primary）
ALTER SYSTEM SWITCH LOGFILE;

SELECT dest_id, status, error, gap_status, database_mode, recovery_mode
FROM   v$archive_dest_status
WHERE  dest_id = 2;

SELECT MAX(sequence#) AS last_seq FROM v$archived_log
WHERE  dest_id = 1;
指令意思
SWITCH LOGFILE
強制切換 online redo，產生一個新的 archivelog，方便觀察傳送。
v$archive_dest_status
status=VALID、error 為空、gap_status=NO GAP 代表正常；recovery_mode 顯示 Standby 的套用模式（如 MANAGED REAL TIME APPLY）。
v$archived_log dest_id=1
Primary 本機最新的歸檔序號，拿來跟 Standby 比對。
V3

確認 redo 有收到並套用（Standby 端）

StandbySQL*Plus
為什麼

「收到」和「套用」是兩件事：redo 可能已經傳到但 MRP 停了。要同時看傳送延遲（transport lag）與套用延遲（apply lag）。

SQL*Plus（Standby）
-- 傳送與套用的延遲
SELECT name, value, time_computed FROM v$dataguard_stats
WHERE  name IN ('transport lag', 'apply lag');

-- 最近的 archivelog 是否已套用
SELECT sequence#, first_time, applied FROM v$archived_log
ORDER  BY sequence# DESC FETCH FIRST 5 ROWS ONLY;

-- 是否有缺號（gap）
SELECT * FROM v$archive_gap;
指令意思
transport lag
Standby 收到的 redo 比 Primary 落後多久，正常為 +00 00:00:00 或幾秒。
apply lag
已收到但尚未套用的時間差，Real-Time Apply 時應接近 0。
applied
YES 已套用；IN-MEMORY 正在套用中，也是正常的。
v$archive_gap
有資料代表缺少某些序號，正常情況 FAL 會自動補上。
預期結果

Standby 最新 sequence# 與 V2 的 last_seq 相同，且 applied 為 YES / IN-MEMORY；兩個 lag 都在數秒內。

V4

實際寫資料，到 Standby 查得到

兩台SQL*Plus
為什麼

系統視圖顯示正常，仍不等於使用者資料真的過去了。最直接的證據是：在 Primary 的 PDB 寫一筆資料，到 Standby 查得到。這裡先停 MRP 再唯讀開啟，查完再回到 MOUNT，就不會用到 Active Data Guard 授權功能。

① Primary：寫入測試資料
ALTER SESSION SET CONTAINER = {{PDB}};
CREATE TABLE lab.dg_test (id NUMBER, note VARCHAR2(50), created DATE DEFAULT SYSDATE);
INSERT INTO lab.dg_test (id, note) VALUES (1, 'written on primary');
COMMIT;

ALTER SESSION SET CONTAINER = CDB$ROOT;
ALTER SYSTEM ARCHIVE LOG CURRENT;
② Standby：唯讀開啟查詢後恢復
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;
ALTER DATABASE OPEN READ ONLY;
ALTER PLUGGABLE DATABASE {{PDB}} OPEN READ ONLY;

ALTER SESSION SET CONTAINER = {{PDB}};
SELECT * FROM lab.dg_test;

-- 恢復成 MOUNT + 套用
ALTER SESSION SET CONTAINER = CDB$ROOT;
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;
指令意思
ARCHIVE LOG CURRENT
歸檔目前的 online redo，並等待歸檔完成，確保剛才的交易已送出。
RECOVER ... CANCEL
停止 MRP。Standby 必須停止套用後才能以非 ADG 方式開啟。
OPEN READ ONLY
以唯讀方式開啟 Standby，只能查詢，不能寫入。
SHUTDOWN → STARTUP MOUNT
回到 MOUNT 狀態再啟動 MRP。若直接在 READ ONLY 下啟動 MRP 就會變成 Active Data Guard。
預期結果

Standby 查到 1 | written on primary。

切換測試：能不能正常切換

W1

Switchover 前檢查

兩台SQL*Plus
為什麼

Switchover 要求 Standby 已經套用完所有 redo，否則會失敗或等待很久。VERIFY 會預先檢查參數、SRL、落差等條件，但不會真的切換，等於彩排。

SQL*Plus
-- Primary
SELECT switchover_status FROM v$database;     -- TO STANDBY 或 SESSIONS ACTIVE
ALTER DATABASE SWITCHOVER TO {{STB}} VERIFY;

-- Standby
SELECT name, value FROM v$dataguard_stats WHERE name = 'apply lag';
指令意思
SWITCHOVER TO ... VERIFY
12c 起的語法。回應 Database altered. 代表通過；若有問題會回傳 ORA-16475 等錯誤，詳細原因寫在 alert log。
SESSIONS ACTIVE
仍有使用者連線，切換時 Oracle 會將其中斷，練習環境可以直接切換。
W2

Switchover：Primary ↔ Standby 互換

兩台SQL*Plus
為什麼

這是 Data Guard 的核心能力：計畫性維護（主機更新、搬機房、演練）時把服務移到另一台，而且零資料遺失。指令從舊 Primary 發出，Oracle 會確保最後的 redo 都送到並套用完才轉換角色。

① 原 Primary（{{PRI_HOST}}）
ALTER DATABASE SWITCHOVER TO {{STB}};
② 新 Primary（{{STB_HOST}}）
SELECT database_role, open_mode FROM v$database;   -- PRIMARY / MOUNTED
ALTER DATABASE OPEN;
ALTER PLUGGABLE DATABASE ALL OPEN;
③ 新 Standby（{{PRI_HOST}}）
-- 原 Primary 在 switchover 後會被關閉；若仍在執行，先 SHUTDOWN ABORT
STARTUP MOUNT;
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;
指令意思
SWITCHOVER TO {{STB}}
一行完成：原 Primary 送出最後的 redo（End-Of-Redo）→ 轉成 standby → Standby 套用完畢轉成 primary。
ALTER DATABASE OPEN（新 Primary）
新 Primary 轉換後停在 MOUNTED，需要開啟才能服務。
STARTUP MOUNT + RECOVER（新 Standby）
原 Primary 現在是 Standby，掛載後啟動 MRP 開始接收、套用新 Primary 的 redo。D4 預先設好的 fal_server 與 VALID_FOR 這時派上用場。
W3

驗證新角色與反向同步

兩台SQL*Plus
為什麼

「切過去」只成功一半，還要確認方向反過來的同步也正常：新 Primary 的資料能送回原 Primary 主機。這也證明兩邊的參數都正確設定為對稱。

SQL*Plus
-- 兩台：確認角色已互換
SELECT db_unique_name, database_role, open_mode FROM v$database;

-- 新 Primary（{{STB_HOST}}）寫資料
ALTER SESSION SET CONTAINER = {{PDB}};
INSERT INTO lab.dg_test (id, note) VALUES (2, 'written on {{STB}}');
COMMIT;
ALTER SESSION SET CONTAINER = CDB$ROOT;
ALTER SYSTEM ARCHIVE LOG CURRENT;

SELECT dest_id, status, error FROM v$archive_dest_status WHERE dest_id = 2;

-- 新 Standby（{{PRI_HOST}}）
SELECT sequence#, applied FROM v$archived_log
ORDER  BY sequence# DESC FETCH FIRST 3 ROWS ONLY;
預期結果

{{STB}} 為 PRIMARY / READ WRITE，{{CDB}} 為 PHYSICAL STANDBY / MOUNTED；新 Primary 的 dest_2 為 VALID；新 Standby 的最新序號已套用。可用 V4 的方式在 {{PRI_HOST}} 唯讀查到 id=2。

兩台SQL*Plus
為什麼

能切過去、也能切回來，才算驗證完整。指令完全一樣，只是方向相反，執行主機也互換。

① 目前 Primary（{{STB_HOST}}）
ALTER DATABASE SWITCHOVER TO {{CDB}} VERIFY;
ALTER DATABASE SWITCHOVER TO {{CDB}};
② 回到 Primary（{{PRI_HOST}}）
ALTER DATABASE OPEN;
ALTER PLUGGABLE DATABASE ALL OPEN;
③ 回到 Standby（{{STB_HOST}}）

回到 V1 的角色表，lab.dg_test 在 Primary 上有 id=1、2 兩筆。

F1

（進階）Failover 與 Reinstate 舊 Primary

兩台SQL*Plus
為什麼

真正的災難是 Primary 突然掛掉，沒有機會做 Switchover。Failover 會把 Standby 強制升為 Primary，ASYNC 模式下可能遺失最後幾秒的交易。之後舊 Primary 的時間線已經「分岔」，要用 Flashback 倒回分岔點再轉成 Standby（reinstate），這就是 D2 要開 FLASHBACK 的原因。

① 模擬 Primary 當機（{{PRI_HOST}}）
SHUTDOWN ABORT;
② Standby 接手（{{STB_HOST}}）
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;
ALTER DATABASE FAILOVER TO {{STB}};
ALTER DATABASE OPEN;
ALTER PLUGGABLE DATABASE ALL OPEN;

-- 記下分岔點 SCN
SELECT TO_CHAR(standby_became_primary_scn) AS scn FROM v$database;
③ Reinstate 舊 Primary（{{PRI_HOST}}）
STARTUP MOUNT;
FLASHBACK DATABASE TO SCN 1234567;      -- ← 換成上一步的 SCN
ALTER DATABASE CONVERT TO PHYSICAL STANDBY;
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;
指令意思
FAILOVER TO {{STB}}
12c 起的語法：套用所有已收到的 redo 後，把 Standby 轉為 Primary。
standby_became_primary_scn
Standby 成為 Primary 時的 SCN，也就是兩條時間線的分岔點。
FLASHBACK DATABASE TO SCN
利用 flashback log 把舊 Primary 倒回分岔點，丟掉它在分岔後獨有的變更。
CONVERT TO PHYSICAL STANDBY
把控制檔轉為 standby 控制檔，之後重新掛載並啟動 MRP 開始接收新 Primary 的 redo。
收尾

Reinstate 完成並確認同步後，再做一次 W2 的 Switchover（從 {{STB_HOST}} 切到 {{CDB}}），就能回到原本的角色配置。

K1

（選用）改用 Data Guard Broker 管理

兩台DGMGRL
為什麼

上面的 SQL 方式能看清楚每個動作，但實務上通常用 Broker：一行 SWITCHOVER 就會自動完成兩邊的開啟、掛載、啟動 MRP，也能做狀態檢查與自動 Failover（Fast-Start Failover）。Broker 會接管 log_archive_dest_n 等參數，所以要先清掉手動設定，兩種方式不要混用。

SQL*Plus（兩台）
ALTER SYSTEM SET log_archive_dest_2 = '' SCOPE=BOTH;
ALTER SYSTEM SET dg_broker_start = TRUE SCOPE=BOTH;
DGMGRL（Primary）
dgmgrl sys@{{CDB}}

CREATE CONFIGURATION dg_lab AS
  PRIMARY DATABASE IS {{CDB}} CONNECT IDENTIFIER IS {{CDB}};
ADD DATABASE {{STB}} AS CONNECT IDENTIFIER IS {{STB}} MAINTAINED AS PHYSICAL;
ENABLE CONFIGURATION;

SHOW CONFIGURATION;
VALIDATE DATABASE {{STB}};
SWITCHOVER TO {{STB}};
SHOW CONFIGURATION;
SWITCHOVER TO {{CDB}};
指令意思
dg_broker_start
啟動 Broker 背景程序 DMON。
log_archive_dest_2 = ''

CREATE CONFIGURATION / ADD DATABASE
建立 Broker 組態並加入 Standby，Broker 會自動設定傳送參數。
SHOW CONFIGURATION
最後一行 Configuration Status: SUCCESS 代表一切正常。
VALIDATE DATABASE
檢查 Standby 是否已經準備好接手（Ready for Switchover: Yes）。
SWITCHOVER TO
自動完成 W2 的所有步驟，包含重啟兩邊資料庫（需要 D5 的 _DGMGRL 靜態註冊）。
